# Shortly 코드 검수 및 CapCut 잘림 분석 — 2026-09-07

> 아래 내용은 수정 전 검수 기록이다. 이후 적용한 수정·검증·남은 한계는 [수정 보고서](capcut-framing-fixes-20260907.md)를 따른다. 추가 확인 결과 필수 내용 파서는 조사 단계 5개/160자와 대본 단계 8개/240자가 서로 달랐고, 현재는 두 단계 모두 8개/240자로 통일했다. 마케팅 결말 배제 규칙은 아래 세 경로 외 팩트체크 단계에도 있어 함께 수정했다.

## 범위와 결론

가이드 조사→대본→컷 추천, 개인 에셋 생성·미리보기·검수, CapCut 준비·삽입 경로를 읽고 최근 실제 프로젝트와 비교했다. 저장소 전체 모든 실행 경로의 정상 작동을 보증하는 검수는 아니다. 앱 코드·설정·가이드·CapCut 프로젝트는 수정하지 않았다. 유료 생성과 실제 CapCut 렌더링도 실행하지 않았다.

핵심 결론: 생성 에셋의 구도를 보존하는 공통 계약이 없다. 이미지 상단 제거, 영상 중앙 크롭, 다른 프로젝트의 마스크 복제, 고정 배율이 따로 작동한다. 원본이 정상이어도 출력에서 잘림·크기 불일치가 생길 수 있는 구조다.

## 우선순위별 발견 사항

### P1. 생성 이미지 상단 25%를 일률적으로 제거한다 — 확인됨

- 근거: `shortly/generate/capcut_export.py:678` `_crop_generated_image_safe_top`, 템플릿 내보내기의 호출 지점 `:2745` 부근.
- 이미지 생성 프롬프트에서 상단 25%를 자막 여백으로 요청하지만, 실제 생성물이 이를 지켰는지 확인하지 않는다. `generated_image` 분류면 내보내기 복사본에서 해당 영역을 물리적으로 잘라낸다. 수동 업로드된 생성 이미지에도 분류만 같으면 적용될 수 있다.
- 실제 `미국 마트를 지배한 냉동김밥/shortly_cuts/cut_02.png`, `cut_05.png`, `cut_07.png`, `cut_09.png`는 원본 1024×1536에서 1024×1152로 변했다. 네 파일 모두 원본 상단 384px를 제거한 결과와 픽셀이 완전히 일치했다.
- 직접 열어 본 `cut_07.png`에서는 제거된 영역이 주로 천장이고 두 사람의 얼굴·김밥은 남아 있었다. 따라서 이 샘플의 얼굴이 실제로 잘렸다고 단정하지 않는다. 다만 내용과 무관하게 자르는 동작과 종횡비 변경은 확정이다.
- 원본 생성 파일은 보존된다. 손실은 CapCut 프로젝트에 복사된 파일에 발생하므로 재생성 없이 재배치할 여지가 있다.
- 권장: 기본은 원본 보존. 상단 제거는 에셋별 명시적인 구도 정보가 있을 때 비파괴 crop으로 적용하고, 전체 보기/채우기를 선택할 수 있게 한다.

### P1. 영상에 임의의 최근 프로젝트 마스크가 복제된다 — 확인됨, 실제 가림 범위는 렌더 확인 필요

- 근거: `capcut_export.py:495` `_pick_generated_video_mask_template`, `:533` `_attach_common_mask`.
- 최근 프로젝트 최대 80개를 훑어 `cut_*.mp4`에 붙은 첫 `common_mask`를 선택한다. 채널·템플릿·원본 비율·마스크 형태·수동 편집 여부를 검사하지 않는다. 이미 자동 생성된 프로젝트에서 같은 마스크를 다시 가져올 수도 있다.
- 현재 선택되는 마스크는 `resource_type=mirror`, `height=0.390730444785276`, `centerY=-0.004907967746714852`이다. 김밥 프로젝트의 자동 영상 `cut_01`, `cut_06`, `cut_08`과 도시락 프로젝트의 `cut_02`, `cut_05`에 같은 설정이 붙어 있다.
- `common_mask`가 있다는 이유만으로 자막 안전 영역에 맞는 마스크라는 보장이 없다. 이 값이 화면을 정확히 몇 퍼센트 가리는지는 CapCut 마스크 좌표 해석과 렌더 확인 없이 단정하지 않는다.
- 권장: 채널별 명시적인 콘텐츠 표시 영역과 승인된 마스크를 사용한다. 다른 프로젝트의 최근 편집 상태에 출력이 좌우되지 않도록 한다.

### P1. 영상은 실제 콘텐츠 프레임과 무관하게 먼저 9:16으로 중앙 크롭한다 — 확인됨

- 근거: `capcut_export.py:427` `_center_crop_for_vertical`, `:829` `_build_photo_segment`.
- 3:4 원본은 좌우 각각 12.5%, 총 가로 25%가 제거된다. 16:9 원본은 좌우 각각 약 34.18%, 총 가로 약 68.36%가 제거된다. 여기에 마스크가 추가된다.
- 현재 확인한 김밥·도시락 자동 영상 소재는 720×1280(9:16)이며 crop 좌표가 0~1 전체 영역이다. 따라서 **이 샘플들의 문제를 좌우 중앙 크롭 탓이라고 단정하면 안 된다.** 이 경우에는 마스크와 배율·위치를 우선 확인해야 한다.
- 권장: 1080×1920 전체 캔버스와 본문 에셋 표시 영역을 구분하고, 그 표시 영역을 기준으로 한 번만 맞춘다. 가로 영상을 세로로 채우기 전에 잘릴 영역을 보여준다.

### P2. 미리보기와 내보내기의 구도가 다르고, 배치가 고정값이다 — 확인됨

- 근거: `shortly/apps/personal/automation/api.py:403` 원본 미리보기, `static/assets.html:36` object-fit:contain, `capcut_export.py:347` `_reference_asset_layout`.
- 미리보기는 원본 우선으로 보여주지만 내보내기는 별도 crop·마스크를 적용한다. UI에서 최종 잘림을 예측할 수 없다.
- 이미지는 종횡비 구간별 scale/y 상수, 영상은 항상 0.86/0.02를 사용한다. 현재 김밥 이미지들은 상단 제거 후 scale=0.72/y=-0.12, 영상은 scale=0.86/y=0.02이다. 원본 크기 및 마스크도 달라 숫자만 비교해 실제 크기 차이를 단정할 수는 없지만 동일한 프레임 계산을 공유하지 않는 것은 확실하다.
- 이름과 달리 `_reference_asset_layout`은 실제 레퍼런스의 콘텐츠 사각형을 측정하지 않는다. 레퍼런스는 소재 구조를 가져오는 데 쓰이고 배치는 상수다.
- 권장: 이미지·영상이 동일한 표시 영역 모델과 미리보기를 공유하도록 한다. 컷별 위치, 배율, crop, 전체 보기/채우기 값을 저장한다.

### P2. 검수가 실제 화면 손상을 탐지하지 못하고, CapCut 저장 경로를 누락으로 오인한다 — 확인됨

- 근거: `shortly/apps/personal/automation/capcut_assets.py:159`, `:231`, `:252`; `automation/review.py:43`, `:83`.
- CapCut 검사는 파일·참조·음소거와 마스크 존재를 확인한다. 마스크의 모양·위치나 얼굴·제품 잘림을 검사하지 않는다.
- Qwen 검수에는 이미지/영상 프레임 없이 manifest JSON이 전달된다. 현재 기능은 컷 계획에 대한 텍스트 검수이며 완성 영상의 시각 검수가 아니다.
- CapCut에서 다시 저장된 두 프로젝트의 소재 경로는 `##_draftpath_placeholder_…_##/shortly_cuts/...` 형식이다. 검수기는 이를 실제 파일 경로처럼 검사하여 김밥 7개, 도시락 5개 소재를 누락으로 판정했다. 프로젝트 내부 파일은 존재한다. 이는 실제 삭제가 아니라 placeholder 미해석에 따른 오탐이다.
- 권장: 프로젝트 기준 placeholder 해석, 실제 media probe, 표시 영역 검증을 먼저 추가한다. 이후 최종 화면 프레임을 이용한 검수를 별도로 도입한다.

### P1. 같은 제목으로 새 가이드를 생성하면 기존 저장본을 덮어쓸 수 있다 — 코드 확인, 재현을 위한 실제 저장은 실행 안 함

- 근거: `shortly/service.py:757` 제목 slug 경로 + exist_ok=True, 이후 request/script/guide 파일 저장. 수정 기능은 `:1140` 부근에서 `_unique_output_dir`를 사용하지만 일반 생성은 사용하지 않는다.
- 제목 고정 후 다시 생성하면 과거 대본·에셋 연결 맥락을 잃을 수 있다. 이번에는 실제 데이터 변경이나 과거 소실 원인 확정을 하지 않았다.
- 권장: 생성마다 별도 ID/폴더를 만들고 제목은 표시용으로 관리한다. 최소 수정은 일반 생성에도 고유 출력 디렉터리를 적용하는 것이다.

### P2. 4초 생성 영상과 더 긴 컷의 충돌을 검사하지 않는다 — 코드 확인, 현재 샘플에서는 초과 미발견

### P2. 과거 대본 보완이 새 소재에 과도한 금지 규칙으로 남아 있다 — 코드 확인, 실제 LLM 결과는 미실행

- 근거: `shortly/generate/script_gen.py:74`와 `:791`, `shortly/generate/research.py:1004`.
- 연구 요약·대본 생성·최종 흐름 정리 단계 모두 마케팅/기념 캠페인을 결말에서 제외하도록 강하게 지시한다. 예외는 '사용자가 마케팅 전략을 요청한 경우'로 좁다.
- 이번 불닭의 페리 복귀 파티는 사용자와 합의한 핵심 결말인데도 곁가지로 분류되거나 삭제될 위험이 있다. 실제 모델 호출 없이 삭제 결과를 확정하지는 않았다.
- 권장: 사용자 지정 핵심 결말 > 해당 주제의 직접적인 결과 > 일반 편집 휴리스틱 순서를 명시하고 모든 단계에서 같은 우선순위를 공유한다. 특정 단어의 등장만으로 캠페인을 배제하지 않는다.
- 이번 입력 프롬프트에는 페리 행사를 결말의 필수 장면으로 명시하고, 리콜을 복귀 홍보로 전환한 대응까지 다룬다고 적었다. 프롬프트만으로 시스템 규칙과의 충돌을 완전히 해결한다고 보장하지 않는다.

### P2. 조사 입력과 본문 읽기의 제한이 화면 안내보다 좁다 — 확인됨

- 근거: `research.py:98` parse_research_focus / parse_required_content, `:627` 본문 발췌, `:692` web_search.
- 추가 조사/필수 내용은 각각 최대 5항목, 항목당 160자로 잘린다. UI에는 이 상한이 표시되지 않는다.
- 검색 본문은 쿼리에 '공식/자료/연혁'이 있을 때 상위 두 결과만 최대 5,000자 발췌한다. PDF는 본문 읽기에서 제외된다. 입력 URL 전체를 반드시 방문·정독하는 구조가 아니다.
- 이번 DTU PDF의 계산 경위를 링크만으로 모델이 읽는다고 가정하면 안 된다. 따라서 확인된 요지를 입력에 포함하고 조사 항목은 5줄로 구성했다.
- 권장: 입력 한도 표시, 사용자 지정 출처의 직접 읽기, PDF 지원 또는 미지원 명시, 사실별 근거 상태를 사용자에게 노출한다.

## 이미 작동하는 보호 장치

- 이미지 내보내기는 원본 파일을 우선 선택한다(`prepare_export`). 9:16 prepared 이미지 후처리가 존재하지만, 정상적인 현재 경로에서 그 결과를 다시 사용해 항상 이중 크롭한다고 결론 내리면 안 된다.
- 영상은 volume=0으로 삽입되며 현재 기본 생성 요청은 4초/9:16이다.
- 제목과 같은 CapCut 프로젝트가 이미 있으면 새 타임스탬프 폴더로 내보낸다. 기존 프로젝트를 직접 덮어쓰는 동작과 가이드 저장 덮어쓰기 문제는 별개다.
- 대본 생성·팩트체크 후 주체 및 수정 범위 보호가 있고, 컷 추천은 별도 LLM 단계에서 수행한다. 이번 검수에서 상용 모델을 호출하지 않았다.

## 권장 첫 보완 순서

1. CapCut 표시 영역 계약: 원본 보존 + 채널별 콘텐츠 영역 + 이미지/영상 공통 배치 + 임의 프로젝트 마스크 의존 제거.
2. 그 계약과 같은 결과를 보여주는 내보내기 미리보기 및 컷별 수동 위치/크롭 값 저장.
3. 같은 제목 새 가이드의 덮어쓰기 방지.
4. placeholder·실제 길이·표시 영역을 포함하는 검증 강화.
5. 사용자 필수 결말 우선순위와 출처 읽기 제한 보완.

기존 완성 프로젝트는 수정하지 않고 별도 비교 프로젝트에서 검증하는 방식이 적합하다. 자막 두 줄 영역·제목·TTS·효과음·음소거·수동 편집 보존을 회귀 기준으로 삼는다. 이미지는 2:3/3:4/1:1, 영상은 9:16/3:4/16:9를 대상으로 얼굴/손/제품이 가장자리에 있는 사례를 확인한다.
